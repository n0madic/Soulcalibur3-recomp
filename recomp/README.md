# Soulcalibur III — static recompilation with PS2Recomp

Target: the PAL release of Soulcalibur III, boot ELF `SCES_533.12` (stripped, MIPS R5900, 12 890 functions).
Tool: [ran-j/PS2Recomp](https://github.com/ran-j/PS2Recomp) at the commit in `PS2Recomp.commit`. Host: macOS arm64 (sse2neon path).

## Version control

Git tracks the port tooling and progress: the patch series (`series`, `upstream/`), dependency commit pins, build and analysis scripts, recompiler configuration/address metadata, and this documentation. The root `.gitignore` allows only those source locations; add new source paths there deliberately. The tooling is under the GPL-3.0 (`../LICENSE`); `../README.md` is the user-facing build and run guide, this file the technical record.

Original game data is supplied locally. The disc image, extracted ELF/IRX/assets, generated game C++, recorded VU microcode, audio/video/frame or memory dumps, Ghidra projects, cloned dependencies, build products and caches are excluded. `recomp/work/` is entirely local; paths to investigation evidence below refer to that untracked directory. No original game binaries or assets are included in the repository.

## Reproduce

Place your own disc image at the repository root (any name ending in `.iso`; the script takes the only one there), or pass its path as `ISO=<path>`. The build script extracts it into the ignored `recomp/work/game/` directory, and stops with a message when it finds none, several, or an image without `SCES_533.12`. `test_build_iso.sh` tests that lookup without building anything.

```sh
brew install molten-vk vulkan-loader ccache   # Vulkan for the GPU GS; ccache is optional
./recomp/build.sh            # extracts the ISO, builds PS2Recomp, recompiles, builds the runner
```

The first full build of the runner takes about 5 minutes on an M1 Pro without ccache (~2100 unity units of generated
code, which include `ps2_runtime.h`, so any runtime header change rebuilds all of them; before the Ghidra far-chunk fix (`0001-recompiler-function-boundaries-and-delay-slots`) six units with
bloated functions took up to an hour on their own). `build.sh` compiles through ccache when it
is installed, so a regeneration that leaves most functions unchanged only recompiles the changed units.

With the Ghidra export (`make ghidra`, then `make build` again) the recompiler takes its function list from `work/ghidra-export/sc3_functions.csv`; every measurement below was made that way. It gives 66 705 functions (the ELF's 12 890 plus resume entries, jump-table targets and data-pointer entries), of which 66 496 are recompiled and 209 are stubs, with 0 decode failures (recompiler log of 2026-10-23), and the 2026-10-26 regeneration wrote 67 806 small files (506 MB). Without the export the analyzer's own list is used, which misses jump-table targets and fall-through labels.

For the movie path, install FFmpeg (`brew install ffmpeg`) and build with `ENABLE_FFMPEG=ON SKIP_INTRO=0 ./recomp/build.sh`; by default both movies are skipped. The PAL release's display-mode dialog (PAL50/PAL60) is answered with PAL60 by `display_mode.toml`; `DISPLAY_DIALOG=1` keeps the dialog.

### Linux (Docker) and Windows (llvm-mingw) builds

Trial builds on other platforms; neither is part of `make build`. Both compile, but they have hardly been tested: macOS on Apple Silicon is the only platform the game has been run and measured on (on Linux it was only started once, headless and on a software Vulkan driver; nothing was run on Windows; no tests, no battle, no sound check).

**Linux arm64 in Docker** (`docker/Dockerfile`: Ubuntu 24.04, clang, the raylib/Vulkan/FFmpeg development packages, xvfb, Mesa lavapipe). Pass `--platform linux/arm64` explicitly: with `DOCKER_DEFAULT_PLATFORM=linux/amd64` the image is x86_64 under emulation, and **Linux x86_64 does not build** (the x86 path of the CMake files adds no `-msse4.1`, and the generated MMI code needs it: `_mm_max_epi32 requires target feature 'sse4.1'`).

```sh
docker build --platform linux/arm64 -t sc3-linux-build recomp/docker
docker volume create sc3-linux-work
docker run --rm --platform linux/arm64 -v "$PWD":/src:ro -v sc3-linux-work:/work sc3-linux-build ./recomp/build.sh /work
```

The work directory is the volume (the disc image is read from the mounted repository). Copy `work/ghidra-export` into `/work/ghidra-export` before the build: without the Ghidra map the game stops on a `missing-target` jump. The runner builds with no errors. To run it headless, start `Xvfb :99`, then `LP_NUM_THREADS=0 ps2EntryRunner SCES_533.12` from `/work/game` with `DISPLAY=:99` (2026-10-28, 4 CPUs and 8 GB for the Docker VM): the game reaches the title screen ("PRESS START BUTTON") in about 2 minutes on lavapipe. lavapipe's own render threads crash with SIGSEGV inside `libvulkan_lvp.so` (not in the game), hence `LP_NUM_THREADS=0`; the resident memory of the game grew from 2.4 GB to 7 GB in 150 s, close to the VM's limit, and a longer run was killed (cause not examined).

**Windows x86_64 cross-compiled on macOS** with [llvm-mingw](https://github.com/mstorsjo/llvm-mingw) (release 20261020, unpacked anywhere; GCC's mingw-w64 from Ubuntu 24.04 is not enough: its headers lack `ID3D12Device4` and one generated unit took over an hour). It builds the runner from an `out/mingw` directory of the tree that `build.sh` has patched and fed with the generated code, and uses the paraLLEl-GS and `PS2_VULKAN_LIBRARY` changes of `0007` (see its details):

```sh
LLVM_MINGW_ROOT=<llvm-mingw dir> ./recomp/docker/build-mingw.sh recomp/work
```

The result is `recomp/work/PS2Recomp/out/mingw/ps2xRuntime/ps2EntryRunner.exe` (PE32+ x86-64, imports `libc++.dll` and `libunwind.dll`; no FFmpeg, no VU profiles). It has not been run on Windows.

## Patch series

`series` lists the patches `build.sh` applies to PS2Recomp, in order: 20 local patches (`NNNN-*.patch`) and 15 upstream PRs (`upstream/NN-prNNN-*.patch`) interleaved with them. Until 2026-10-27 the series had 72 patches, one per fix; patches that fixed or extended an earlier one, or that belong to one problem area, are now merged into one patch per area. The result is byte-identical: applying the old and the new series to the base commit gives the same tree, which passes the same tests (560 of 560; 562 of 562 since `upstream/15` and the 16-deep frame ring, 2026-10-27).

Rules for the series: an upstream PR stays a separate patch, as the PR has it (only test registration lines merged), so it can be dropped when the PR is merged; local fixes of an upstream patch live in a local patch after it. **Do not stack a new patch on top for every fix, as the series did before.** A fix, an extension or a test for something an existing patch already covers goes into that patch (re-make it in a clean checkout, see CLAUDE.md), and the patch's row in the tables below and its details are updated. Only a new problem area gets a new numbered patch and a line in `series`. A patch that only corrects another one is a sign that it belongs in that one.

### Details of the former patches

**`0001-recompiler-function-boundaries-and-delay-slots.patch`**

- **0001**: Recompiler fix (see below).
- **0004**: Recompiler fix: stub/syscall/library starts are registered before the resume entries of an enclosing function (see fix 6), with a regression test in `ps2xTest`.
- **0033**: **Fixes the freeze after a demo round.** When a block ends with a branch whose delay slot lies past its end (the slot is decoded since `0001`), the not-taken path continues after the slot; that address is now registered as a resume point of the function containing it. In SC3 the Ghidra map cuts `FUN_001f73e0` into resume wrappers, and `entry_001f7830` starts at the delay slot of the `bc0t` at `0x1f782c` (it is also the target of the `bc0f` loop, so it must stay an entry). A thread resumed in `entry_001f7798` ran the `bc0t` and its slot and handed `0x1f7834` to the EE scheduler, which had no function there and made the main thread dormant: the picture froze on the winner's pose in 2 of 3 runs. Upstream PRs #371 and #368 avoid function starts at delay slots for heuristic and pointer-table starts; that does not apply here. Needs a regeneration of the game code.
- **0047**: **Build time.** The Ghidra CSV gives `End` as the highest address of a body, and a body with a far chunk (a shared tail reached by a jump) then spans every function in between; the recompiler decoded all of it with an entry at every address. `FUN_003b6428` has Size 32 but End `0x3D2D08` and came out as 25 770 instructions (9.4 MB of C++); 18 such functions added 0.31M instructions, and the six units holding the largest ones took 4-61 minutes each, so a full build of the runner took ~66 minutes while all other units finished after ~10. A span that exceeds Size now ends at the next function start of the map (labels such as `entry_`/`caseD_` do not count); the 2 907 bodies with only small holes keep their End (cutting them at start + size dropped code after the hole: missing target at `0x4368c4`). What the long span stood in for is kept: runs of non-zero words in the cut-away part that no map entry covers become functions (e.g. `0x40abd8`, called by the ADX reader), and a direct branch, jump or call from anywhere into the middle of another function in a cut span gets an `entry_` there (e.g. `JAL 0x406928` from `0x4069c8`); without them the game stopped on a missing target with a black screen. Statically, every direct transfer into an address that only the long spans registered is reachable afterwards, and no data word points there. Result (M1 Pro, no ccache): instructions in the generated code 1.548M -> 1.284M, output 601 -> 506 MB, slowest unit 61 min -> 51 s, full runner build 66 min -> 4.5 min (268 s), `ps2EntryRunner` 192.0 -> 154.4 MB (`__text` 167.7 -> 132.5 MB; the old binary also carried the working tree's diagnostics). The attract loop reaches the demo battle as before. Test: a body with a far chunk ends at the next function, a body with a hole keeps its End, an unreadable Size keeps End, uncovered code becomes a function but zero padding does not, and calls from inside and from outside the span into a function's middle get entries (fails without the cut, without the orphan runs and without the cross-function entries). Needs a regeneration of the game code.

**`0002-mmi-semantics.patch`**

- **0006**: Runtime fix: `PSLLVW`/`PSRLVW`/`PSRAVW` had swapped operands and wrong per-doubleword semantics (see fix 8), with a regression test.
- **0007**: Generator/runtime fix: the remaining MMI opcodes audited against the EE reference (see fix 9). Adds `ps2xTest/src/ps2_mmi_tests.cpp`: a scalar reference model for every helper plus a per-opcode check that generated code reads `rs`/`rt` and writes `rd` as the instruction defines.

**`0003-software-gs-sprite-fast-paths.patch`**

- **0008**: Software GS speed-ups that keep the output bit-identical: per-draw decoded-texel cache for large textured sprites (disabled when the draw can write the texture's pages), flat-colour sprite fill, `lround`-free bilinear rounding. `ps2xTest/src/ps2_gs_raster_tests.cpp` compares both fast paths against the per-pixel path on random VRAM.

**`0004-build-options.patch`**

- **0005**: Adds the `PS2X_ENABLE_LTO` option (default ON); `build.sh` turns it off because the thin-LTO link of ~2100 generated objects took over an hour.
- **0028**: `ps2_runtime.h` only forward-declares `VU1Interpreter` and holds the VU0/VU1 interpreters by `unique_ptr`, so changes to the VU interpreter header no longer rebuild the ~2100 generated translation units.

**`0005-gs-signal-interrupt.patch`**

- **0012**: Runtime fix 10 (see below): GS interrupt (INTC cause 0) from SIGNAL/FINISH, SIGNAL stall while CSR.SIGNAL is pending, INTC causes latched while disabled. Tests in `ps2_gs_tests.cpp` and `ps2_runtime_interrupt_tests.cpp`.
- **0045**: The GS interrupt was raised on a rising edge of the combined line `CSR[0..4] & ~IMR` (`0012`). The game's GS interrupt handler kicks the last GIF packet of a frame from the last SIGNAL; that packet ends with `FINISH`, and only the FINISH interrupt sets the frame-drawn flag (`0x473dce`, set when `0x5bc802` is set). The runtime runs the packet before the handler returns, so FINISH was raised while the SIGNAL was still pending: no new edge, and the handler's acknowledgement (it writes back every CSR bit it read) cleared FINISH. The main loop then waited for the flag until its GS timeout of four fields (`0x12e418`, `s4 * 4` lines) and reset the GS, on every frame. With `0044` that made the game draw a new frame only every 3 VSyncs (~17 fps, slow motion); before `0044` the timeout expired within ~1 ms because Timer 3 ran 36x too fast. Now every event raised unmasked interrupts once, also while another one is pending, and a CSR write forgets the acknowledged events before a queued SIGNAL is applied, so that SIGNAL interrupts as well. Demo battle: 150 consecutive frames with 1 repeat instead of 99; the title scene takes 23 s instead of 67 s and the attract loop reaches the next demo. The fast-motion ghosting (doubled limbs and weapons) is no longer visible in the dumped frames. Test: SIGNAL then FINISH both interrupt, a queued SIGNAL applied by the acknowledgement interrupts (fails with the old line edge, and without forgetting acknowledged events).

**`0006-ee-fpu-semantics.patch`**

- **0030**: EE `CVT.W.S` truncates toward zero and saturates out-of-range values to `0x7FFFFFFF`/`0x80000000` (it rounded to nearest; GCC uses it for every `(int)` cast, 1976 sites in SC3). Same fix as upstream PRs #316 and #383.
- **0032**: **Fixes the torn character meshes.** The EE encodes `SQRT.S fd, ft` with the source in the ft field (fs is 0), unlike MIPS; the translator read fs, so all 165 `SQRT.S` in the game computed `sqrt($f0)`. See "Torn meshes: root cause". Same fix as upstream PRs #382 and #277. Needs a regeneration of the game code.

**`0007-parallel-gs-renderer.patch`**

- **0023**: [paraLLEl-GS](https://github.com/Arntzen-Software/parallel-gs) (Vulkan compute, LGPL-3.0+) as the default GS renderer, selected by `PS2_GS_BACKEND` (see above); built when `PS2X_PARALLEL_GS_DIR` points at a checkout. The GIF arbiter passes the path id to the GS, SIGNAL/FINISH/LABEL reach CSR/SIGLBLID from the GPU GS too, local-to-host transfers read back from it, and the scanout is read back once per vsync for the host window. Also fix 11 and fix 12. GPU tests in `ps2_gs_parallel_tests.cpp` (skipped without Vulkan unless `PS2_TEST_REQUIRE_GPU=1`).
- **Frame context ring (2026-10-27)**: the Vulkan device has `kFrameContexts = 16` Granite frame contexts instead of 4. paraLLEl-GS takes the next frame context in every flush it submits (`GSRenderer::flush_submit`), not once per vsync, and Granite then waits for the GPU work of the context it takes. With 4 the game thread waited for the GPU every fourth flush: a 15 s `sample` of the demo battle put 17.5% of the game thread in `vkWaitSemaphores` under `flush_submit` (4-5 ms per vsync inside `ParallelRenderer::vsync`), although a battle frame costs the GPU only a few ms (a `wait_idle` after each frame waited 1.3-1.6 ms more once the thread had done its own wait). A/B on mains power, 170 s attract-loop runs, two runs per setting: the demo battle ran at 40 game ticks/s with 42-54 new pictures/s with 4 contexts, at 52-60 and 56-60 with 16, at 50-60 and 58-60 with 64; the wait in `vsync` fell from 4-5 ms to 0.6-0.7 ms. `GSParallelRenderer::frameContexts()` reports the device's count and `ps2_gs_parallel_tests.cpp` requires at least 16 (with 4 the test fails).
- **Windows build (2026-10-28)**: `gs_parallel.cpp` loads the Vulkan loader with `LoadLibraryA("vulkan-1.dll")`/`GetProcAddress` on Windows (`PS2_VULKAN_LIBRARY` still overrides), and the runner's CMake turns Granite's `GRANITE_VULKAN_DXGI_INTEROP` off (its `wsi_dxgi.cpp` needs `ID3D12Device4`, which mingw-w64's headers lack; the runtime does not use Granite's WSI). With both, `ps2EntryRunner.exe` cross-compiles on macOS arm64 with llvm-mingw 20261020 (clang 23.1.4, `x86_64-w64-mingw32`, `-msse4.1`: the generated MMI code uses `_mm_max_epi32` and friends, and the x86 path of the CMake files adds no SSE4.1 flag). It has not been run on Windows. The exe imports `libc++.dll` and `libunwind.dll` from llvm-mingw's `x86_64-w64-mingw32/bin`.

**`0010-vu-compiled-programs.patch`**

- **0034**: Runtime for compiled VU1 microprograms (upstream draft PR #254, layer B, adapted to this series): `ps2_vu1_program.h/.cpp` run a generated routine pair by pair with the interpreter's pipeline timing (FMAC/FDIV/EFU latencies, stalls, delayed VI for branches, XGKICK progress), write results when they issue and, when the cycle budget ends mid-program, hand the pending writes back to the interpreter, which continues from there. - **0038**: A compiled routine writes results at issue, the interpreter when their latency ends, and lands a write only if no later one replaced it. - **0040**: Cheaper VU0 macro calls (VCALLMS). - **0041**: `Run::commitFlags` (4% of the game thread in the battle profile) commits the flag results of compiled routines when the code reads MAC, status or CLIP. Battle profile: `commitFlags` 350-387 -> 261 samples of ~8000 (about 1% of the game thread). Covered by the differential fixtures: taking the first CLIP writer or dropping the product sticky bits fails them.

**`0012-ee-timing-and-pacing.patch`**

- **0002**: Runtime/IOP fixes (see below).
- **0043**: Work the EE scheduler did on every guest call although nothing was due (battle profile after `0042`: ~12% of the game thread). (1) `PS2Memory::advanceEeTimers` ran at every checkpoint (every 8-32 EE cycles) with a hash-map lookup of `GIF_STAT` and 64-bit divisions per running timer; the cycles are now added up and the counters catch up only once an interrupt can be due (the existing, rounded-up `cyclesUntilNextEeTimerInterrupt`) or before a timer register is read or written. Splitting the elapsed cycles differently gives the same counts, because the clock remainder carries over exactly. `GIF_STAT` is reached through a pointer taken at initialisation. (2) `EeScheduler::processPendingEvents` took the event mutex three times per call and scanned the deadlines; it now returns at once when no event is posted, no timer interrupt is pending and no deadline is due (`postEvent` and `scheduleEvent` publish those under that mutex). Profile: timers 230 -> 35 samples, mutex lock/unlock ~300 -> out of the top 60, scheduler total ~945 -> ~400 of ~8000. A/B (300 s each, alternating): demo battle 63.1/64.0 -> 72.0/70.6 ticks/s, title 60.8/62.7 -> 67.7/64.8; same scene sequence. Tests: timers stepped one cycle at a time interrupt on the exact cycle, reads see the live count, a register write moves the next interrupt, and `cyclesUntilNextEeTimerInterrupt` counts the cycles not applied yet (passes on the old code too; four mutations of the lazy catch-up fail it); an event posted by guest code is handled before its next dispatch (fails if the fast path ignores posted events); a wakeup that leaves preemption pending switches before the waker continues.
- **0044**: Game timing. The game holds its main loop to the display by busy-waiting until EE Timer 3 is 311 counts past the count its VSync callback stamped, i.e. one PAL field in scan lines (see "Known gaps"); `0002` started Timer 3 at BUSCLK/256, so the wait ended after ~1 ms and the loop ran unpaced. (1) Timer 3 resets to `CUE | CLKS=3` (H-blank), as the BIOS keeps it for its alarms; the H-blank clock is 15625 Hz once SMODE1 selects PAL, 15734 Hz otherwise. (2) The VBlank period is 20 ms in PAL mode instead of a fixed 60 Hz. (3) EE time is an estimate that falls behind real time while the guest spins on a timer, so a read of a timer count first lets the EE clock catch up with host time since the last VBlank, up to the next scheduled event (`EeScheduler::catchUpWithHostTime`). Result (with `0045`): 50 VSyncs per second and a new frame on every VSync in the demo battle. Tests: Timer 3 counts H-blanks from reset and at the PAL rate after SMODE1 selects PAL (fails with BUSCLK/256 or without the PAL rate); a timer read lets the EE clock catch up with host time and stops at the next VBlank (fails without the catch-up or without the cap).
- **0046**: Game speed after `0045`: frames take ~30 ms of host time in the battle, more than a 20 ms field, and the game has a frame skip for that (`0x473dd7`, on in battles: when a frame overruns its period by half a period it runs an extra logic pass without drawing). It never triggered, because the frame period it compares against (`0x473e06`, 0.02 s of Timer 0) came out 1.5-2 fields long. At start-up (`FUN_0012d1b0`) the game counts Timer 0 (BUSCLK/256) over 256 changes of Timer 3, reading Timer 3 once and then until it changes; with `0044` every read let the EE clock jump to host time, so with the host behind, Timer 3 skipped lines between reads and the measured Timer 0 rate was 926 339-1 163 578 Hz instead of 576 000. Now a timer read lets the clock catch up by at most 128 EE cycles (about one poll iteration), so a poll sees every count; and so that code running long without timer reads does not hold the VBlank back, a time slice (65 536 cycles) ends with the clock caught up with host time unless the guest read a timer during it. Result: the game measures 580 006 Hz (period 11 600 = one PAL field), 50 VSyncs per second, and the demo battle runs ~41-44 game ticks per second with the frame skip active instead of ~25 (the title ~50). Tests: polling Timer 3 advances it by at most one per read and still catches up with host time up to the VBlank; the game's calibration loop, with a checkpoint before each read, measures 9437 +-2% Timer 0 counts over 256 PAL lines (20 791 when slices catch up during polling, 11 484 with one line per read, and no VBlank-free 256 changes without the cap); a checkpoint at a slice end catches up with host time (3 lines instead of >= 75 without it).

**`0015-spu2-autodma-and-audio-queue.patch`**

- **0049**: Fixes to `0048`. (1) **AutoDMA**: while ADMAS enables a core, DMA writes queue PCM for its sound data input (blocks of 256 left then 256 right samples), played at 48 kHz and routed by MMIX `0x80`/`0x40`; the transfer ends with the DMA interrupt once its last block is next to play, so the driver's next transfer queues behind it without a gap. The CRI ADX driver streams this way (core 0, 2048-byte halves of a 4096-byte loop buffer); before, each transfer completed after a fixed delay and went to sound RAM, so the title streamed 200 MB in 3 s and played nothing. (2) The shared volume registers (MVOL, EVOL, AVOL, BVOL at `0x760 + 0x28 * core`) were decoded as core 1 registers and ignored. (3) AVOL scales the external input (core 0 into core 1) and BVOL the sound data input, as in PCSX2 (`ExtVol`/`InpVol`); `0048` had them swapped. Tests (`ps2_iop_spu2_tests`): the input plays left and right from their halves, the transfer ends only when its last block is next and a transfer queued then follows without a gap, clearing ADMAS drops the input, BVOL/AVOL each mute only their input, MVOLX reads back, and a DMA through the IOP registers with ADMAS set does not complete after a fixed delay (each fails with the corresponding mutation).
- **0057**: **Deliver SPU2 AutoDMA completions at their sample.** The completion interrupt makes CRI's driver queue the next block. `IopSpu2::samplesUntilAutoDmaDone()` predicts when either core takes its queued transfer in; `advanceSpu` generates up to that sample and stops there, the SPU2 also runs while IOP code executes (batches of 32 samples or up to the next completion), and idle steps end at the next completion (at most 256 samples) counted from the SPU2's state. The first version used fixed 256-sample idle steps counted from the last poll, which delivered a core's completion up to 255 samples late when the two cores were out of phase. In manual 36 s captures, core-1 empty input samples fell from **65947 to 0**. Tests: the predictor; a synthetic IRX starts core 0's AutoDMA, spins about 100 samples and starts core 1's, and one long idle run must deliver core 0's interrupt within 8 samples (fails before the patch and with the fixed-step version).
- **0058**: **Remove periodic PCM cuts.** The old host queue trimmed about 125 ms whenever latency passed 250 ms (**18003 frames cut** in a capture). The queue is now `PcmQueue` (`runtime/ps2_pcm_queue.h`, no raylib): the host resamples by at most ±2% toward an 83 ms target, with Catmull-Rom interpolation (linear interpolation kept only 71% of a 12 kHz tone between samples); a backlog beyond four times the target (after a stall or a burst) is still cut once to the target instead of being played off at +2% for up to a minute. Tests: interpolation endpoints and a 12 kHz tone at a half-sample offset; 30 s at the host rate and 60 s 1% fast play without gaps or cuts and settle near the target; a 0.9 s backlog is cut once; an empty queue is silent until 50 ms are queued.

**`0018-gs-presentation-and-super-sampling.patch`**

- **0065**: **Doubled images in fast motion.** The host loop latched a new picture whenever the vsync tick changed. paraLLEl-GS publishes a vsync's picture on the next vsync, and the scheduler advances the tick before it scans out, so the host often latched the old picture again and then skipped the next one. `GS::latchNewHostPresentationFrame` latches only a picture that is new: by the renderer's read-back sequence on the GPU path, by the vsync tick on the CPU path. - **0066**: **Sharper picture.** `PS2_GS_SSAA` (1, 4, 8 or 16; the default was 8 until `0069`) sets paraLLEl-GS's super-sampling. paraLLEl-GS shows the samples only when it scans out at twice the resolution, so any rate above 1 also enables `high_resolution_scanout`. ## Doubled images in fast motion (`0065`)

Measured with temporary counters in the paraLLEl-GS read-back (2026-10-26, M1 Pro on mains power, attract loop):

## Intro ADX counter: root cause

Established with the original CRI ADX IRX and controlled reproductions on 2026-10-24. The game supplies `thpri=39` and `spucore=2` when loading `CRI_ADXI.IRX`, but two IOP emulation defects prevent the driver from accepting them:

1. `IopEmulator::Impl::loadImage` calls the IRX entry with `(argumentSize, flatArgumentBuffer)`. The IRX expects `(argc, argv)`, including a guest array of string pointers. Its entry wrapper does not convert the flat buffer. The observed argument buffer is 20 bytes, beginning with `0x72706874` (`thpr`); the two nonempty options belong in `argv[1]` and `argv[2]`. Preserving the final empty entry in this 20-byte buffer gives `argc=4`, including the module name at `argv[0]`.
2. `IopSysclib::dispatchImport`, ordinal 8 (`look_ctype_table`), always returns zero. CRI's option parser requires digit bit `0x04` before calling `strtol`, so correcting `argc/argv` alone still leaves both numeric options ignored.

Consequently, CRI keeps its default SPU2 core **0** instead of mode **2** (both cores, with new streams defaulting to core 1). The intro's PSM stream is assigned to core 0. The game's normal audio update (`FUN_002a9408`) sees no active core-0 stream among its five ordinary ADXT handles; Sofdec's separate movie handle is outside that list. With the passthrough guard `0x4F3880=0` (normal PCM movie init flags are 1), the call at **`0x2A96A8`** stops core 0: `0x3F6E60` → `0x40B620` → ADX RPC **`0x411`, argument 0** → IOP `0x53B90` → `0x54240` → `0x5820C` → `sceSdBlockTrans(0, 2, ...)`. This disables its AutoDMA and clears its PSMOUT active flag. Core 1's DMA interrupts and PSM semaphore signals continue; the core-0 stream's PCM queues stop being consumed.

The EE decoder eventually fills its queues at 16,896 decoded samples. ADXT's played-sample calculation (`0x3FDE70`, decoded minus unplayed queued data) remains **512/48000**, causing the Sofdec frame gate described above to reject subsequent timestamps.

| Controlled run | CRI selected mode | Actual ADX counter | Decoder requests |
| --- | --- | --- | --- |
| Original | 0 | Stays at 512/48000 | 6 |
| Correct `argc/argv` only | 0; ctype still rejects digits | Stays at 512/48000 | 6 |
| Correct `argc/argv` and ctype | 2 | 165888 → 214528 → 304384 → 390080 → 483584 / 48000 | At least 304 in a bounded 35 s run |

The last run also produces nonzero SPU2 audio. No audio counter or presentation clock was overridden. This confirms the counter's root cause; complete playback and realtime speed were not established. The original temporary diagnostic changes were removed, preserving the earlier working-tree changes. Production patch `0054` now implements the general IRX startup ABI and ctype behavior, with no game addresses or diagnostic switches. ### Remaining crackle: MPEG decode pacing (`0059`)

The previous empty-buffer and dropped-frame counts did **not** prove the signal was intact. After the user reported crackle in both movies, a PCM comparison with the original ADX track found inserted near-silent spans in whole **256-sample** units. SPU2's queue was filled with those samples, so its missing-input counter remained zero. The IOP mixer at `0x556A4` takes the no-full-source-block branch at `0x557D0` and generates silence. Its output thread still receives alternating DMA half-buffer callbacks; no half-buffer transitions are lost.

The cause is a second presentation throttle in the HLE `sceMpegGetPicture`. Its timing assumes **60000/1001 Hz** VBlank and uses two fields for this **30000/1001 fps** source. This PAL game actually runs at **50 Hz**, so the low-level decoder yields only **25 fps**. Sofdec's video queue then blocks its shared SFD demux; audio runs short after the initial buffer drains. The 35-second THX audio stretches to roughly 42 seconds with short inserted silences. Sofdec already gates video presentation on the real ADX clock, so this additional decoder wait is inappropriate for its native toIPU path.

`0059` skips only that HLE wait for the active native IPU decoder. HLE `sceMpegAddBs`/PSS users retain their existing pacing. In a manual A/B comparison, the source interval 5.2–8.0 s has **25 near-silent inserted spans before and none after**. Later samples stay at one fixed offset from the original ADX, rather than drifting by whole silent blocks. No ADX counter, audio rate or cached presentation clock is overridden by this correction.

### Remaining rhythmic crackle: IOP thread continuation (`0060`)

The remaining rhythmic crackle was a separate **right-channel PCM corruption**. Earlier `0059` waveform checks measured the left channel, so they did not establish stereo integrity. A 35 s capture rules out the host converter and mixer: converter output equals its input after a constant one-sample delay, and the final mix is that output multiplied by 0.6875. Peaks are 0.801 before the mix and 0.551 after it, with no full-scale clipping. A separate 45 s run has 0 late callbacks over 4000 calls (maximum interval 10.088 ms, processing 0.159 ms, lock waiting 0.005 ms). The user confirmed the same audible defect in `0060-mixed-listen.wav`.

Both outputs of the original EE ADX decoder match the source. The right channel is already wrong in the EE → IOP SIF payload, before SPU2: many chunks match samples **8192 frames later**, exactly one PCM ring generation (171 ms). Native SJR queue tracing finds the first unequal reservation: 2048 bytes free on the left, 1024 on the right. The stereo decoder uses the left size for both outputs, overwriting unsent right-channel data. The error accumulates and periodically changes generation, producing the rhythmic clicks; stronger samples make each discontinuity louder.

`IopKernel::beginNextReady` selected the lowest thread ID after every host execution budget. CRI threads 7 and 10 both run at priority 39, so waking thread 7 preempted thread 10 between stereo operations, including inside an interrupt-disabled critical section. Those boundaries are emulator pauses, not guest yields. `0060` keeps a FIFO ready queue per priority: a thread that was running keeps the head of its priority across host slices and preemptions, and only a guest yield sends it to the tail; interrupt suspension prevents preemption during a critical section.

In the manual A/B captures, retaining only interrupt-disabled execution delayed the error but still corrupted the right channel by source second 24. Preserving the running equal-priority thread removes all length mismatches across 1576 paired producer commits. Both output channels correlate 0.9998–0.9999 with the source in the active THX passages, including seconds 24–31; the old right channel often correlated only 0.09–0.22 while the left was correct. Separate interrupt-delivery changes are unnecessary and are reverted. The production patch contains only the IOP scheduler change; temporary EE decoder, SIF, SPU2 and host audio probes are removed. ## Torn meshes: root cause

Symptoms in the demo battle: stretched limbs, legs drawn as thin sticks, faces with black eye sockets and exposed teeth (already on the static VS screen), large translucent garbage polygons. Traced backwards with temporary probes:

1. A check on every VIF1 `UNPACK V4-32` upload for rigid 4x4 matrices found the face-bone matrices with a row of ~1e18 (the same broken 3x3 on nine bones near head height). The DMA snapshot matched guest memory, so the data was already wrong on the EE.
2. A host watchpoint on one of those matrices showed that `FUN_00101058` (a 4x4 matrix multiply) writes it; its local-bone input already held `-3.4e38` (the PS2 `x / 0` result), built by the face-expression loop in `FUN_001ca3a0`.
3. That loop turns each face bone's base matrix into scale + quaternion: `func_102420` extracts the row lengths, the loop divides by them, `func_100480` converts the unscaled matrix to a quaternion and `func_1006D0` slerps toward the expression pose. The Y scale always came out 0, so `1/0` gave the PS2 maximum and the quaternion became `(3.4e38, 0.5, 0.5, 0.5)`.
4. `func_102420` takes the Y length with `sqrt.s $f2, $f2` (`0x46020084`: ft = 2, fs = 0). The EE reads the operand of `SQRT.S` from ft; the translator read fs, i.e. `$f0`.

Ruled out on the way: VU1 programs cut off by the cycle budget (none), the game writing matrices after kicking the DMA (snapshot equals memory), VIF0 (only `STCYCL` + `UNPACK V4-32`, handled correctly). Real but unrelated deviations found on the way are `0030` and `0031`.

## Black screen: root cause (found with Ghidra)

The "wait condition" was in the disc I/O driver. The game links CRI's ADXPS2 library (also used as its file
reader). Its init (`FUN_003f5a58`) creates four worker threads (`0x3f4fd0`, `0x3f50c0`, `0x3f51c8`, `0x3f52b8`),
and a vblank INTC handler (`0x1503b0`) wakes them every frame. The workers issue the real `sceCdRead` calls.
Two runtime bugs kept them from ever running, so the game's request queue (`FsInit` task reading `ROOT.OLK`)
never completed and nothing was loaded:

1. `CreateThread` rejected priority 0 (`KE_ILLEGAL_PRIORITY`). ADXPS2 reads the main thread's priority via
   `ReferThreadStatus` (0) and passes it as the new thread's initial priority, then calls `ChangeThreadPriority`.
2. `ChangeThreadPriority` returned 0 instead of the previous priority. ADXPS2 uses its critical-section pattern
   `old = ChangeThreadPriority(self, 1); ...; ChangeThreadPriority(self, old)`; with `old == 0` the restore failed
   (`-403`) and the main thread stayed at priority 1, starving the workers (priorities 8-25).

Both are fixed in `0013-kernel-memory-and-dma.patch` (the former `0003`). After that the game reads `ROOT.OLK` (index sectors, then
512-sector bulk reads) and the worker threads run.

How it was found (all in `ghidra_scripts/`, run with `analyzeHeadless -process SCES_533.12 -noanalysis`):
`FindCallers.java` (caller chains), `DumpDecomp.java` (decompile functions), `Xrefs.java` (references to a global).
Main loop: `entry -> FUN_0018e508 -> FUN_0012d1b0` (init) `-> while (FUN_0012d9e0() == 1) FUN_002ac728()`;
`FUN_0012d9e0` is the per-frame render/timing function, game logic runs as a task list (`FUN_00128488`, names such
as `FsInit` / `MainJob`) updated through function pointers.

Next obstacle after the fix: indirect calls and jump-table dispatches to addresses that the heuristic function
list does not know (`missing-target`). Two measures:

- `ghidra_export.sh` exports Ghidra's function and label map (`make ghidra`); `build.sh` passes it as `ghidra_output`
  (66 502 entries instead of 12 890, ~600 MB of generated C++).
- `pointer_entries.py` adds all code addresses referenced by data words (vtables, callback tables) as entry points
  in a second recompiler pass.

The condition itself has not been identified. Next step: trace the callers of the polling code in the main loop (`0x10d618`, `0x10e4d8`, `0x12e26c`, `0x4182xx`) in Ghidra, or log every runtime stub call in steady state.

Performance: the EE thread rasterises GS primitives synchronously inside GIF DMA writes (`GSCpuBackend`, software, per-texel `ReadTexture` with an 8 KB page copy on every page change). The ~13 full-screen textured blends per frame dominate the run time. Batching the IOP scheduling (`IopEmulator::runEeCycles`) and `EeScheduler::checkpointDue` accounting was tried and did not change the frame rate, so both changes were reverted.

## Fixes found along the way (each was a real blocker)

1. **Delay slot dropped at function end** (`0001`). Without Ghidra the function boundaries are heuristic; a function ended right before the delay slot of its final `jr $ra` (`addiu $sp,$sp,0x40`). The recompiler replaced it with a NOP, leaking stack and eventually returning to garbage (`jump to 0x5c0000`). `decodeFunction` now also decodes the delay slot of a branch that is the last instruction of a function. Upstream-worthy; no regression test was added yet (the `ps2xTest` target is not built in this setup).
2. **`sceCdLayerSearchFile` (0x4293D0) recompiled as guest code** (`sc3.toml`). It talks to the CDVDFSV RPC server (SID `0x80000597`) that does not exist in the emulated IOP, so `sceSifBindRpc` looped forever. It is now stubbed with the runtime's `sceCdSearchFile` handler.
3. **Unbound-client RPC at 0x428410** (`sc3.toml`). Stubbed with `ret0`. The analyzer labels it `scePadSetDmaCallback`, which is probably a wrong name from signature matching. The real behaviour is unverified.
4. **IOP heap too small** (`0002`). `IopMemory::HeapBase` was `0x120000`, leaving ~0.9 MB; the game allocates 0x96000 + 0x2d000 + 0x41040 + ... bytes. Lowered to `0x90000`; the last IRX is loaded at `0x52600`, so the new base is expected to clear all modules, but the module end addresses were not measured. Modules loaded later at runtime could collide with the heap.
5. **EE Timer 3 never ran** (`0002`). The game busy-waits on `0x10001800`; the runtime started all timers stopped. Timer 3 started with `CUE | CLKS=2`, a guess and a wrong one: the game counts scan lines on it, and `0044` starts it on H-blanks.
6. **Stub shadowed by an enclosing Ghidra function** (`0004`). The Ghidra CSV `End` column is the highest address of a (possibly non-contiguous) body, so 8 225 entries overlap other functions, e.g. `FUN_00432e00` spans `0x432E00..0x43CC38`. `FunctionTableEmitter` registered resume entries of such a function before stubs, so the start of the `_calloc_r` stub (`0x43B870`) ran the guest `calloc` instead. That code clears the block by the allocator's chunk header, which the runtime's HLE allocator does not have: size `0 - 4`, `memset(0xfffffffc)` wiped the whole RAM. Found by logging `ra` in the runtime's `memset` and decompiling the caller in Ghidra.
7. **Computed jump into undefined code** (`sc3.toml`). `FUN_00100ac0` (VU0 macro-mode code) jumps to `0x100b4c + idx * 0x10`; Ghidra ends the function at `0x100b4c`, so the four blocks and their common tail (`0x100b80`) were unknown. Added as entry points.
8. **Packed variable shifts translated wrongly** (`0006`). The generator emits `PS2_PSRLVW(rs, rt)` but the runtime macro took `(value, count)`, so `psrlvw $a1,$a1,$zero` always produced 0. The helpers also shifted all four words instead of the low word of each doubleword with sign extension. `FUN_001b03a8` (a clamp + table lookup built from `pminw`/`psrlvw`/`pmaxw`) therefore always returned table entry 0, and the demo-battle character picker (`FUN_0019c718`) looped forever after the title screen. Found by sampling the hung process (the main thread sat in `FUN_0019c718` and the RNG) and decompiling the loop in Ghidra.
9. **Other MMI opcodes translated wrongly** (`0007`). Audit of every MMI translation against the EE reference, prompted by fix 8. Used by the game: `PABSW`/`PABSH` read `rs` instead of `rt` (generated `pabsw rd, $zero`, always 0; 7 sites in the game, incl. entry `0x18c688`) and did not saturate `0x80000000`; `PADDUH`/`PSUBUH` wrapped instead of saturating; `PMULTH` summed the products into one value instead of spreading eight products over HI/LO (9 sites around `0x110000`); `PEXEW`, `PEXCW`, `PROT3W` used wrong permutations. Not used by the game but also wrong: `PINTH`/`PINTEH`, `PEXEH`/`PEXCH`, `PMADDW`/`PMSUBW`/`PMULTW`/`PMADDUW`/`PMULTUW` (unsigned, single accumulator instead of two lanes), `PMADDH`/`PMSUBH`/`PHMADH`/`PHMSBH`, `PDIVW`/`PDIVUW`/`PDIVBW`, `PMFHI`/`PMFLO`/`PMTHI`/`PMTLO` (only 64/32 bits moved), `PMFHL.*`, `PMTHL.LW`; `PSLLH`/`PSRLH`/`PSRAH` now mask the shift amount to 4 bits. `PREVH` reversed all eight halfwords instead of four per 64-bit half. The SA register is now a byte count like in PCSX2 (`MTSAB` unscaled, `MTSAH` shifted by 1, `MTSA`/`MFSA` unscaled, `QFSRV` shifts by SA*8 bits); before, `MTSA` with a byte count shifted by too few bits (the game has `MTSA`/`MFSA` next to 54 `QFSRV`). The test reference models were cross-checked against PCSX2 `MMI.cpp`/`R5900OpcodeImpl.cpp`, which also corrected `PMFHL.SH` word order and the `PHMSBH` odd words (NOT of the odd product). `PMADDW`/`PMSUBW` keep the architectural `{HI,LO} += product` rule; PCSX2 additionally emulates a hardware multiplication error there (not used by the game). Ops with HI/LO side effects are now emitted as helper calls that run even when `rd` is `$zero`.
10. **GS interrupt never raised** (`0012`). The game ends each frame's VIF1 and GIF chains with a GS `SIGNAL` and continues them from its GS interrupt handler (`FUN_0010e660`, INTC cause 0): when both SIGNAL ids (VIF1 id 2, GIF id 1) are in `SIGLBLID` it restarts both channels after the END tag (`TADR + (QWC+1)*16`), and that continuation carries the 8192-bucket ordering table with all 2D/3D packets. The runtime set `CSR.SIGNAL` but never raised INTC cause 0, so only the frame-setup chains (clears and the feedback blend) reached the GS: the black title screen and the missing text. Three parts were needed: (a) a GS interrupt line `CSR[0..4] & ~IMR[8..12]`, edge-triggered and checked after DMA kicks and CSR/IMR writes (`IMR` now resets to `0x7F00`; `0045` makes it interrupt per event instead of per line edge); (b) a `SIGNAL` written while `CSR.SIGNAL` is still pending waits (FIFO) until the guest acknowledges `CSR.SIGNAL`, like the GS stall (PCSX2 queues it the same way): the handler restarts both chains before acknowledging, so the second id was lost; (c) an INTC cause raised while disabled is latched and delivered on `EnableIntc`: the handler runs with causes 0..2 disabled and re-arms through `IMR`, so the follow-up interrupt arrived while cause 0 was off and was dropped. Found by dumping the VIF1 chain (4 tags per frame, ending with `SIGNAL`), walking the ordering table it never reached, and decompiling the handler registered with `AddIntcHandler(0, 0x10e660)`.
11. **Display mode never programmed** (`0023`). The game calls `sceGsResetGraph`, which `sc3.toml` stubs with the runtime's HLE version. That HLE built a GIF packet with made-up register addresses for the privileged registers (`0x41`/`0x42` for PMODE/SMODE2 are really `SCISSOR_2` and `ALPHA_1`, `0x59`-`0x5f` for DISPFB/DISPLAY/BGCOLOR), so it clobbered two drawing registers and never set SMODE1. The software GS did not care, but paraLLEl-GS reads the video format from SMODE1 (`LC`, `CMOD`) and refused to scan out ("Unknown video format"). `sceGsResetGraph` now writes the privileged registers directly, and `SetGsCrt` / `sceGsResetGraph` share `gsSetCrt`, which programs SMODE2 and the SMODE1 line clock and colour mode for NTSC, PAL, VESA and HDTV. Tests in `ps2_gs_tests.cpp`.
12. **GS cache tests did not link** (`0023`). `ps2xTest/gs_cache` builds the GS sources on their own, without `ps2_memory.cpp`; since `0012` moved the SIGNAL handling into `gsWriteSignal` (defined there) the three `gs_cache` suites failed to link, which went unnoticed because only `ps2x_tests` was built. The privileged-register helpers (`gsWriteSignal`, `gsApplyQueuedSignal`, `gsSetCrt`, `gsWriteFinish`, `gsWriteLabel`) now live in `src/lib/gs/gs_priv_registers.cpp`, which `gs_cache` builds along with the paraLLEl-GS stub. Build all test targets (`cmake --build <dir>`, then `ctest` in `ps2xTest`) to catch this.

### Profile and experiments of 2026-10-27

- **Profile of the demo battle with 4 frame contexts (2026-10-27, 15 s `sample` of the game thread, mains power):** blocked 20% (17.5% of it the frame-context wait fixed in `0007`), compiled VU routines 18% plus their run glue 3.4%, recompiled game code 15%, IOP emulation 9% (R3000 interpreter, kernel, SPU2 mixing), VU interpreter functions 4.4% (XGKICK hand-off and entry glue, not interpreted programs), `PS2Memory`/VIF1/`memmove` 3.3%, EE scheduler and timers 2.9%, GS/GIF path 2.3%. VIF1, VU1 and the GIF run synchronously on the EE thread inside the DMA kick (`PS2Memory::processPendingTransfers` 31% inclusive), where the hardware runs them beside the EE; a thread for them was tried (`experimental/gs-pipeline-thread.patch`, two items below). No EE code is interpreted: a call to a function that was not recompiled is reported as `missing-target`, and the runs had none. Open upstream PRs checked against this profile: #380 (a GIF packet is not copied when the arbiter queue is empty) is taken for its GIF half (`upstream/15`; no measurable effect), #328 (EE timers and the IOP serviced every 4096 cycles instead of every 8 or 32) was measured and is not taken (next item), #332 (cap the VBlank pacing debt) has not been tried. #285 (maintainer's GS work) hands paraLLEl-GS's picture to OpenGL through exported Vulkan memory, which MoltenVK does not offer, and #254 is the base of `0010-vu-compiled-programs`.
- **Upstream PR #328 (EE timers and IOP serviced every 4096 cycles) makes the demo battle slower here (2026-10-27, not taken).** Alternating runs of 170 s with a synthetic Start in the first movie and the keyboard off (mains power), VSyncs per second in the battle: no quantum 57.9-59.6 (eight runs); quantum 4096 52.9-53.9 (four runs); 1024 54.6 and 55.7; 256 53.2 and 54.0. The EE clock then runs at 260-265 instead of 285-293 million cycles per host second (real time is 295) with the EE thread still at 0-2% idle, and the title scene that follows runs at up to 67 VSyncs/s to pay back the lag (the VBlank host schedule is never forgiven; see upstream #332). The IOP itself gets cheaper (10.9% of the game thread's samples in the battle, 4.4% with the quantum). The slowdown does not come from the timers: with the EE timers advanced on every call and only the IOP batched, 4096 is as slow (53.2 and 53.9) and 256 loses about 2% (57.1 and 58.8, against 59.3 and 59.6 in the same session); it follows the delay of IOP service, so more of the game's EE/IOP hand-offs (RPCs, ADX and SPU2 streaming) wait for the next quantum. The cause is not pinned down. That the quantum also delayed the GIF_STAT FQC drain (done in `advanceEeTimers`) and timer polling (`0012`) is refuted by the run with per-call timers. The PR was written for a title whose EE spins on a vsync flag while the IOP streams; here the IOP already skips idle time (`0012`).
- **VIF1, VU1 and the GIF on a worker thread work but do not speed up the battle (2026-10-27, experiment: `experimental/gs-pipeline-thread.patch`, not in the series).** `PS2_GS_THREAD=1` hands what a DMA kick gives VIF1 and the GIF to a worker (`GsPipeline`): the VIF1 interpreter, the VU1 programs it starts and the GIF packets that reach the GS. The data of normal-mode transfers is copied at the kick (chains are copied already), so the guest may reuse its memory at once; VIF0 and VU0 stay on the EE thread. The EE thread waits for the worker before it touches what the worker touches (GIF and VIF registers and FIFOs, VU1 memory, GS privileged registers, IMR, the HLE GS routines, the native GIF chain paths, and each VBlank, before it is stamped). A kick runs on the calling thread while the guest has the VU1 D or T break bits set. 11 new tests, and a negative control for each barrier and for the snapshot. Three findings: (1) the GS interrupt had to be latched when the event is raised (`GSRegisters::irqLatch`): the game's own wait loop polls CSR, which waits for the worker, sees FINISH and acknowledges it before the scheduler polls the interrupt; the interrupt was lost, its handler never set the flag the loop waits for, and the loop ran into its watchdog (3 fields) on every frame: the title ran at 14 logic steps/s instead of 60, while the VSync rate stayed at 60 (a run judged by VSyncs alone would have passed; read the counter at `0x4f3814` beside it). (2) With that fixed the title runs at 60 and the battle at the same 59 VSyncs/s and 56 steps/s as without the worker (EE idle 0-5%). (3) The cause is the game's own structure: it builds the whole display list, kicks it in about 21 kicks within a short time and then polls CSR for FINISH in `FUN_0010e660` (a `read64` of CSR is where 1131 of 1134 barrier samples sit), so the EE thread waits for the worker for 40% of the time while the worker works for 42%: the two do not overlap. Letting `sceGsSyncPath` return without waiting changed nothing, for the same reason. The 31% of the EE thread that VIF1, VU1 and the GIF take is therefore not recoverable by a thread unless the game's frame structure changes (a frame buffered deeper, which the game does not do). The patch stays as a record and for other games; it changes nothing when `PS2_GS_THREAD` is not set.

In the emulator that loop is not held to the display at all. It never blocks (only two library threads sleep, once per VSync each), calls `sceGsSyncV` once at start-up, and the free-running Timer0 it sets up (BUSCLK/256, only extended to 32 bits on overflow) does not pace it either. With Timer 3 on H-blanks (`0044`, before `0045`) the loop waits: 48-58 displayed frames and ~60 VSyncs per second, but only 10-20 scene updates per second, because during the busy-wait the emulated EE clock advances about three times slower than real time (each poll costs far more host time than the cycles it is charged). Also open: the game runs in PAL mode (the 0.1988 catch-up step), while the runtime's VBlank is fixed at 60 Hz and its H-blank at the NTSC rate. Compare builds by VSyncs per second and read the logic counter beside it (CLAUDE.md, "Speed": the VSyncs follow the emulator's clock and can stay at 60 while the game itself runs slowly). `0044` fixes all three; the low update rate that remained was the lost FINISH interrupt (`0045`): every frame waited for the four-field GS timeout. With both, the demo battle shows a new frame on each of 50 VSyncs per second. The host still needs ~30 ms per battle frame, so the game now relies on its frame skip (`0046`): about 25 drawn frames and ~41-44 logic steps per second against the ~60 of a full-speed PAL game.

**Controller initialization fix:** `experimental/ps2-native-sif-command-completion.patch` applies to this alternative checkout, **not** to PS2Recomp or `series`. Its original `sifcmd` import 28 (`sceSifSendCmdIntr`) was bound to the ordinary command-send handler, which discarded the completion callback and its argument. The patch schedules the callback with the existing SIF DMA completion job, after the transfer and in IOP interrupt context, for imports 28 and 29. No game-specific addresses are used in the runtime fix.

The patch includes a synthetic IOP-module regression test (`ps2sifcmdtest`): ordinary and interrupt command sends, null callbacks, stack-passed callback arguments, payload visibility, deferred completion, interrupt context, and exactly-once delivery. It reports eight failed checks before the fix and zero afterwards. In the game, PADMAN now finishes its analog/motor setup without `VBLANK OVERLAP`, and scripted Start reaches the memory-card prompt. Logs and captured frames stay under the local checkout (`pad-probe.log`, `pad-fixed.log`, `pad-navigation.log`, `games/sc3/pad-fixed-shots/`). The upstream `ps2padtest` also has an existing mismatch with queued frame input: it polls SDL and immediately reads SIO2 without advancing a VBlank. It was examined but is not changed by this patch.
